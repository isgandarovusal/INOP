# Audit directions and authorization — package 2

Directions are hr, service, standard, occupational-safety. Only explicit safety alias normalizes to occupational-safety. Routine/Follow-up/Surprise/Complaint-driven are NOT inferred directions. Recruitment roles/resources are unchanged.

AuditorProfile uses User ObjectId as its Mongo _id, so the built-in _id unique key permits one profile per user without a startup index/backfill. Direction is scalar enum, organization gfc, active boolean. History is embedded and atomically records previous/new direction, actor, reason and date. GET /auditor-profiles/me and GET/PUT /auditor-profiles/:userId use existing audit/audit.assignment grants; management requires admin/audit_manager role AND explicit all permission. Role alone never grants access. No production role/user changes.

Audit permission middleware reads the current profile, not JWT claims. Built-in auditor without active profile fails closed. Custom audit roles keep their existing DB scope unless explicitly given an AuditorProfile, which then restricts them too. Do not classify arbitrary custom roles as auditors from their names: a future role classification migration needs explicit review. Known profiles restrict parent/child/analytics reads to their direction and verified GFC restaurants. Child filters derive allowed parent IDs even for all scope; dashboard endpoint also enforces the profile. Canonical template/source catalog reads are similarly scoped. Frontend metadata includes auditDirection; route/sidebar gates complement but never replace backend checks.

New verified audits have a separate server-owned AuditContext; legacy Audit arbitrary metadata never becomes trusted provenance. No legacy context is auto-backfilled. Management scopes continue to expose unknown legacy records for review. Legacy auditor visibility requires a canonical type/explicit alias and existing verified restaurant link. Unknown legacy direction/organization stays inaccessible to auditors. Historical policy changes do not delete data.

Assignments and profile changes use MongoDB transactions. Both write/increment the same profile version, creating a write conflict and retry instead of racing. Direction changes block while assigned/accepted/started assignments exist. Repeated same audit/user assignment returns the existing row; assignedBy is the authenticated actor. No client status/provenance is trusted. Duplicate legacy rows are not deleted. Transactions require replica-set or mongos; unsupported standalone returns 503 before writes. No unsafe nontransaction fallback.

Migration preparation only: inspect/prepare profile/context collections and Mongo validators (scalar direction enum, gfc organization, matching _id/user identity, history structure). Preserve existing validators. Profile _id uniqueness is already guaranteed by Mongo; any future separate userId index must be reviewed before creation. Review legacy assignment duplicates before proposing auditId+auditor unique index; transaction/profile coordination covers authorized new assignments meanwhile. No production createIndexes/collMod/seed/backfill was run. Production must support transactions; provision profiles/restaurants explicitly before auditors can work. No profile is inferred from previous audits.

Local QA uses a new isolated mongo:7.0 replica-set on localhost:27018 with RAM-backed data; the pre-existing localhost:27017 instance/volumes are unchanged. Fixture setup creates synthetic profiles/restaurants only inside owned random test DBs. Production schema auto-index settings stay unchanged.
