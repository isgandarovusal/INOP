# Audit lifecycle safety — package 4

New audits always begin draft. Client derived scores, passed flags, risk, approval metadata and archive/provenance are discarded. Only server-resolved immutable revision defines required question IDs/types. Unknown/duplicate/incomplete answers are rejected on submission. The existing service yes/no/na ratio is computed server-side over non-N/A answers; all-N/A produces null, not a fabricated 100%. No standard, HR, numeric weights or pass thresholds are invented. Undefined contracts remain unscored; legacy results are never silently recalculated. Old records are read as before; new legacy submissions are explicitly legacy-unscored drafts.

Execution answers cannot supply trusted numeric scores/risk. Submission binds its existing snapshot and updates execution/parent atomically. Standard UI blocks incomplete checklist and does not show an empty 100%; safety preview denominator uses the complete existing legacy checklist, not the number of created answer records. These legacy UI previews are NOT a new scoring contract. Server does not certify them without reviewed revision rules.

Approval create must be pending, with an active independent reviewer who has current approval permission and parent access. Client approved status is rejected. Resolution requires the designated reviewer or explicitly permitted audit manager/admin, and never the requester (including admin). Resolved decisions cannot be overwritten. Approval/finding/status/closure operations lock the same audit in transactions; current auditor profile is rechecked/locked for writes. Required-answer checks and open finding checks guard closure. Explicit PATCH /audit-findings/:id/status closes findings; official activity/provenance is server-created. Closure completes assignments atomically. Closed audit mutation is rejected; historical legacy closure needs separate reviewed migration rather than a fabricated certification.

The state graph is draft→scheduled/in-progress/cancelled; scheduled→in-progress/cancelled; in-progress→completed/cancelled; legacy failed/completed→in-progress; cancelled→draft. Completed requires bound complete revision. A closed audit requires a separately reviewed reopening workflow and cannot be casually reopened. Generic PUT cannot change status/scoring/template/identity. Assignment repetitions return existing record, assignedBy is server-owned, and explicit DELETE assignment now marks revoked with history; it does not erase the row. Profile creation blocks unresolved legacy active assignments.

Audit/Restaurant DELETE archive instead of hard-delete, preserving audit/child/FK history. Parent scopes exclude archived audits; restaurant IDs remain intact. Templates already retire rather than delete. No cascade deletion, historical recomputation or backfill occurs.

Generic evidence uses real bounded validated private uploads, AuditEvidence metadata, authorized GET and no-store attachment delivery. Temporary blob URLs are rejected as permanent references. Upload creates evidence and activity with audit lock in a transaction. Browser FormData sends actual bytes. Existing historical blob URLs cannot be recovered from metadata alone and are not fabricated.

IMPORTANT production blocker: Render Free local filesystem is ephemeral. Production evidence POST explicitly returns 503 until a durable private storage adapter is approved/configured; local uploads use the existing private filesystem for isolated QA only. Do not claim these files survive Render redeployment. No new cloud credentials/bucket or dependency is created. Database/file commit is not a cross-system transaction: uncertain upload outcomes require a reviewed orphan reconciliation policy; never delete referenced originals blindly.

Migration needs: replica-set/mongos for transactional writes, optional schema/validator additions, audited profile/context/revision provisioning, review of legacy active assignments/templates/results. Production autoIndex/backfill remain off. Unknown production roles/data are not changed. Regression assertions that previously expected physical deletion, client-approved creation or incomplete certification must be updated to the safer explicit contracts; those unsafe expectations are not compatibility guarantees.
