# Scoped GFC HR analytics

GET `/api/hr/analytics` returns `hr-analytics-v1`. It requires existing application.read and recruitment.read grants, intersecting each resource's independent server scope. Aggregation ownership IDs are explicitly cast to ObjectId; Mongo aggregation does not perform Mongoose find() casting. No role-name shortcut or new permission grant is introduced. None/missing/missing-department scopes fail closed.

Filters: brandId (including `unset`), branchId, jobId, source, canonical Application status, from/to (`YYYY-MM-DD`, UTC calendar days, inclusive). Invalid keys, query objects, dates and IDs return 400. Application counters use the filtered Application/Job intersection. Active vacancies count current Open Jobs within the same Job/brand/branch scope; Application source/status/date filters do not redefine whether a vacancy is active. This distinction is stated in the UI. A closed Job can still have legitimate historical Applications.

Mongo aggregates funnel, source, review, duplicate-file alerts, interview results, delivery queue and duration samples. Main pipeline projects event type/time/status/delivery state only, removing HR notes and email/provider internals. Candidate lookup independently applies candidate.read and projects only the required metadata. Parent denial never contributes review/duplicate/score facts; Application totals may remain visible while these metrics show restricted/partial coverage. CV review currently counts distinct readable profiles **linked to the filtered Applications**, not the future unmatched external-ingestion queue (packages 10/11). Identical file hashes are review alerts, not a person identity or automatic merge.

Current-stage time requires an actual saved stageEnteredAt. Time-to-hire requires a server Hired transition timestamp and creation date, using the latest such transition for currently Hired Applications. Missing legacy history is excluded from samples; no dates are inferred. No samples yield null, while a real measured zero remains zero. Current-stage duration is elapsed calendar time, not historical working hours.

Score distribution applies the same `ats-v1` version/hash checks and independently readable Candidate/Job parents as Application matching responses. An internal cursor streams only matching fact fields in batches of 250; CV content, contacts, extracted evidence and checklists are excluded. The API returns bucket/state counts, never these internal facts. This avoids materializing all score rows or a >16 MiB facet array. It is not an AI call. The metric facet and score scan share the same scoped cohort filter; concurrent additions/removals producing a count mismatch hide scores and ask for refresh (`scoreScanConsistent=false`). This is not a transactional point-in-time snapshot; large-data latency/CPU/query behavior is measured in package 08. Aggregations have a 10-second database execution bound; timeout is a handled 503.

Options are independently scoped, max 50 Jobs/branches/brands, titles max 200 characters; truncation is explicit. Actual totals are computed before catalog/group caps. No Candidate names, email/phone, CV hashes, protected traits, history notes or secrets are returned. Brand/branch selection is not authorization. More than 50 catalogs require narrower selection; searchable lookup follows in 08.

New manual Applications store server source `manual`; canonical CV pipeline records `cv_upload`. Client source overrides are ignored. Legacy missing/unknown source remains unknown; no migration/backfill is run. Reserved external source labels do not imply a connected integration. AI/Outlook/external adapters are currently not integrated, local filesystem durability is unverified, and SMTP configuration presence is distinct from actual receipt. Packages 09–12 update these health contracts after adapter implementation; real external evidence remains separate from mock tests.

Frontend `/app/recruitment/analytics` adds GFC and KFC/Pizza Hut/Simit Sarayı views, dependent filters, scoped KPIs/tables, explicit empty/unknown/partial states and read cancellation. Language changes reuse loaded data; auth/filter changes hide stale results, and late requests cannot replace new metrics. Filters remain editable after a failed request. The existing main Dashboard, Audit and Execution endpoints are unchanged.
