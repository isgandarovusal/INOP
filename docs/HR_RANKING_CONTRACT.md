# Current full-vacancy Application ranking

`GET /api/hr/v2/application-ranking?jobId=<id>&pageSize=30&after=<cursor>` is additive; existing list/detail contracts stay available. A specific independently readable Job is required (hidden/missing both 404). Primary `application.read` scope is intersected before scanning and counting; Candidate visibility is checked independently. Denied Candidate parents remain null with restricted scores rather than leaking names, criteria or scores.

The response retains `hr-page-v1`: items, page, pageSize (default 30/max 100), total, hasMore and nextCursor. The server scans the entire authorized vacancy cohort, verifies current `ats-v1` Job/Candidate input fingerprints and orders trusted calculated scores descending, then createdAt/_id descending. Real zero sorts above unscored data; stale, legacy, pending, incomplete and restricted scores receive no percentage credit. The internal order sentinel -1 is not returned as a score.

The scan uses an Application cursor and at most 250 scoped Candidate facts per batch, with no per-Application database query. It retains at most pageSize + 1 order keys, yielding to the HTTP event loop during each batch. It does not retain the full cohort in Node memory. Only the selected page is populated and clipped with the existing safe list projection; full evidence remains an authorized detail read on demand. Scanning still costs O(cohort size); package 08D must measure large-data query behavior/latency before making any performance claim.

Ranking cursors are HMAC signed using the existing backend JWT secret with a separate purpose prefix, expire after ten minutes, and bind user/role/department/grants, vacancy, page size, cohort digest and score/date/id boundary. They are pagination markers, not authorization credentials. Tampering or context mismatch returns 400. Changed observed cohort returns 409 `RANKING_CHANGED`; the UI retains the primary Job and offers retry from page one. A ten-second scan budget or Mongo timeout returns retryable 503. The current JWT and server role/scope are rechecked before completing a long scan; selected scores and the Job fingerprint are checked again before response.

This is not a Mongo transaction or frozen snapshot. A concurrent off-page write after its batch was scanned can be observed on the next scan, triggering cursor restart; a complete atomic live-cohort guarantee is not claimed. No automatic hiring/rejection or score recomputation occurs during this GET. Legacy data is not rewritten.

JobDetail uses signed cursor history for next/back, global ordinals and the total scoped cohort count. Language changes do not refetch; actor/role/permission/route changes reset and cancel old reads. Denied profiles have no clickable names. Authorized profile links are native keyboard-accessible buttons separate from nested score controls. The multi-vacancy Applications table continues to label its own display-page ordering explicitly; it does not invent comparable cross-vacancy scores.

Local index inventory adds non-unique `{ jobId: 1, _id: 1 }` for the stable scan. Existing unique Job/Candidate and other indexes remain. No production index build/migration runs in this package. Deployment preparation must inventory/build additive indexes only with the required production authorization.

Reproduction: the old UI with 35 synthetic applications places “New zero 34” first while the older 100% applicant is absent from the newest page. `hrRanking.test.cjs` covers whole-cohort order, scopes/counts/redaction, stable cursor traversal, forged/borrowed cursors, changed Candidate/Job facts, live permission revocation and empty/legacy data. `hrRankingUI.test.cjs` covers the older best applicant, 30-row limit, next/back ordinals, true zero, language/StrictMode request behavior, explicit 409 restart, stale routes, denied parents and keyboard access.
