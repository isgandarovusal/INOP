# 10C2–10C5 — durable private parsing and HR review

## Implemented local contract

`hrCvProcessing.service.createProcessing` provides enqueue/get/list/runOnce/start/stop for **parse of an existing, identified Candidate original only**. 10C3 connects additive authenticated Candidate routes, an opt-in Native worker and the Candidate detail HR panel. There is no automatic upload/public intake/seed/migration/provider call. Runtime constructor and worker are disabled unless HR_CV_PROCESSING_ENABLED=true; no flag is set. OCR, AI and external ingestion job types are explicitly unavailable, not fake successes. Existing synchronous CRUD/parse and SMTP worker continue unchanged. CV double upload/drafts remain AUD-073, not solved by this foundation.

Enqueue body is only kind=parse, expected original SHA and Candidate revision; actor is the server-authenticated request's User ID. Current active User/Role is loaded from DB, independent Candidate read AND update scopes must include the record, original/hash/revision/source fingerprint must match, and actor/source are rechecked before insertion/replay. Request role/permission/file/actor fields are rejected. HTTP routes use existing JWT/auth middleware, bind child job to parent Candidate and revalidate JWT/current role and parent source before response. No token/credential is stored.

## Additive HTTP and UI contract

- GET /api/candidates/:id/processing — current Candidate read; latest 20 rows sorted createdAt/id descending, {items,limit:20}; metadata only, no result/lease/actor/paths/raw text.
- GET /api/candidates/:id/processing/:jobId — current Candidate read and exact parent membership; private structured result only for the current source fingerprint. Otherwise currentSource=false and result omitted. SHA/revision alone are insufficient: updatedAt, complete original metadata, URL/blob reference and parser identity participate in the fingerprint.
- POST /api/candidates/:id/processing — independent current read AND update; {kind:"parse",expectedHash,expectedRevision}; 202 accepted/replayed. No synchronous parse or Candidate mutation.

All responses are private/no-store. Invalid ID/body 400, missing/invalid/revoked JWT 401, no grant/changed authority 403, inaccessible parent/foreign child 404, stale source 409, bounded queue exhaustion 429, disabled/missing DDL 503. Parent and child 404 codes differ without exposing the child. Role, department and assignment scopes use the existing server policy. Missing/failed processing never disguises itself as an empty success. Native /health remains basic app health, not processing/storage readiness.

The actual Candidate detail panel makes zero processing requests on initial mount, StrictMode or language changes. History/refresh/start/inspect are explicit bounded user actions, with cancellation and current Candidate/auth/source context checks; no automatic POST or polling. Read-only HR may inspect but cannot start. Missing source hash/revision disables start. Auxiliary 500/503/429 or child 404 preserves the primary profile; parent 401/403/404 reloads and masks the primary resource. Source 409 clears retained result facts. Context change/unmount cancels pending responses, including same-revision source timestamp changes.

Success displays rule-based facts, real zero, unknown omission and explicit required HR review in AZ/EN/RU; this is not AI, a hiring decision or automatic field replacement. 10C3–10C4 review remains read-only in the detail panel. 10C5 adds the deliberate current-source edit/draft/confirmation/save flow below. Existing synchronous form review remains available while the queue is disabled.

## 10C4 — bounded authorized repair retry

POST /api/candidates/:id/processing/:jobId/retry uses existing JWT middleware and independent current Candidate read AND update. Body is exactly expectedHash, expectedRevision, expectedUpdatedAt (canonical ISO timestamp) and commandId (UUIDv4). Server records the actual retry actor and timestamp in the private job audit; client actor/role/permission fields are rejected. Command identity is stored as a hash, not exposed with actor IDs in the DTO. Equal command+actor replays one accepted operation, including after worker progress, while the current parent/source/authority still permits it. Different/stale concurrent commands fail 409; they cannot overwrite the accepted operation.

Only blocked SOURCE_MISSING or STORAGE_NOT_CONFIGURED with remaining lifetime attempts and current exact source is eligible. HR must first repair the missing file/storage; retry does not restore bytes, configure secrets or provision storage. OCR_REQUIRED, oversized input/result, cancelled/successful/active/exhausted jobs cannot be retried through this operation. Attempts are never reset: automatic plus manual processing attempts total at most three for this immutable job context; at most two manual reservations. Exhaustion frees slots and remains terminal. A new genuine source produces a separate context; repeated start of the unchanged terminal context never bypasses the cap.

The mutation atomically compares job state/code/attempts/updatedAt and re-reserves existing unique global/original-creator slots. Full capacity returns 429 without changing the job. It preserves the original creator and source context, records the retry caller separately and never substitutes admin/all for revoked original authority. Both original creator and latest retry caller must currently have Candidate read+update before reservation and before/after worker processing. Revocation cancels without a private result; there is no fallback to another actor. An independently authorized admin may explicitly start a new job in their own creator context; this operation does not impersonate them automatically.

New fields manualRetries/retryActorId/retryCommandHash and event actorId are additive optional fields; old rows use manualRetries=0. No new indexes, bulk backfill, DDL or migration is automatically executed. Queue remains disabled by default. UI shows safe manual retry count (including zero) and offers the explicit button only for an eligible current source with update permission. Read-only access is labeled separately from missing identity. 409/429/503 remain auxiliary; stale route/auth response is discarded. No Candidate/profile/score/status write or automatic submission.

One immutable context per original creator/Candidate/source fingerprint/parser-version/kind has a unique index. Equal concurrent requests replay one durable job. Atomic unique partial queue-slot and actor-slot reservations bound active+pending+retry jobs to 64 globally and four per original creator across instances; no count-then-insert limit or unbounded JS queue. Eight bounded allocation tries return 429 if no reservation can be acquired, even if a spare random global slot exists. Terminal state frees reservations. Start still replays successful/blocked/cancelled contexts; manual retry is explicit and preserves the original lifetime attempt bound. This is conservative capacity behavior, not a throughput benchmark or a separate per-retry-caller rate limit.

A worker instance processes one job at a time, bounded 1–4 per run. Mongo atomic claim replaces a lease token, increments attempts and sets a 60-second lease. A 30-second whole-work deadline includes original read, existing bounded document worker and current-scope/source checks. Restart/recreated worker can reclaim expired lease; a stale owner's token/state/lease cannot publish results. Three attempts maximum, persisted 60-second/300-second retry, terminal exhaustion and slot release. Missing source/result/input bounds or unconfigured storage are blocked; lost current authority/changed source cancelled; transient failure/deadline retries then fails. Codes are fixed, no raw error/provider/CV logs. Stop stops polling; it does not undo a job already accepted.

Original is read only through authorized private Candidate filesystem/object reader and exact stored SHA, then real rule-based PDF/DOCX processing. Current worker actor's active DB role/Candidate read+update and full source/revision/parser identity are checked after processing. Structured facts/extraction evidence only (128 KiB maximum), not rawText/sections/file bytes/paths/keys/JWT, are stored privately in select:false result; success requires explicit HR review, never Candidate mutation, score, status, hire/reject or name/contact fabrication. HR may read private facts only with current Candidate read; results from an obsolete source/revision are withheld. Real zero and unknown parsed values retain parser semantics. Empty scan is blocked OCR_REQUIRED; no OCR implementation claimed.

Mongo durability applies to job metadata/results, not a lost ephemeral Native CV file. A recreated worker encountering missing legacy bytes is blocked; it cannot recover an original that was never backed up. No TTL/deletion/default retention period is invented. Terminal metadata/results need approved retention/anonymization/recovery work before real CV acceptance. Per-operation/document/slot limits are not a cap on total collection history or all process/native memory.

## Local DDL and release gate

New collection: `hrcvprocessingjobs`. Schema autoCreate=false/autoIndex=false. No production DDL or automatic startup collection/index creation. Enqueue and worker fail closed PROCESSING_QUEUE_NOT_READY if these uniqueness definitions are missing:

- hr_processing_context_unique: contextKey unique
- hr_processing_queue_slot: queueSlot unique, partial queueSlot type number
- hr_processing_actor_slot: actorId + actorSlot unique, partial actorSlot type number

Additional declared traversal indexes: hr_processing_claim (state/nextAttemptAt/leaseUntil/createdAt), hr_processing_candidate (candidateId/createdAt desc/id desc). Local tests create these only inside UUID-owned loopback databases. Before any approved production activation: dry-run index inventory/duplicates/backup, idempotently create exact additive definitions with separate DB approval, verify reservation and rollback/recovery in an approved environment. No bulk legacy rewrite, destructive reset/seed or automatic delete. Rollback disables new queue/intake, lets existing leased work settle or expire and preserves private current-scope metadata/original access; never restore public uploads/old authorization holes.

Before any later job result applies to a draft, match Candidate ID plus original/parser/revision and current source fingerprint; apply/save remains explicit current-authorized HR action. Existing SMTP diagnostics remain separately implemented in 10C1.

## 10C5 — explicit HR approval and historical server provenance

The existing `PUT /api/candidates/:id` accepts an optional `processingApproval` object with exactly `jobId`, `contextHash` and canonical `expectedJobUpdatedAt`. `expectedRevision` (nonnegative safe integer or a canonical multipart decimal string), an explicit `reviewStatus` of confirmed/corrected and at least one editable fact are required. A replacement upload or Candidate-global decision/status cannot be combined with approval. Ordinary legacy saves retain their contract and do not require a job; client extraction/provenance/authorization fields are never trusted.

Approval requires independent current Candidate read AND update, exact child membership, a successful current-source parse job, rules-2 rule-based evidence, original hash/revision/full fingerprint and matching job timestamp. JWT/current Role is refreshed after the asynchronous result read. The final Candidate write compares revision, updatedAt, URL, original metadata, private blob and parser version as well as both resource scopes. Revoked parent/assignment is 404, changed source/concurrent approval is 409, missing confirmation/invalid inputs are 400, auth is 401/403 and disabled processing is 503. Response is private/no-store. No migration/index/automatic job result write or environment change is introduced.

The server derives `cvReview.fields`, warnings, correction list, actor/time and `processingApproval` receipt from the server result plus normalized HR-submitted facts. The receipt records job/parser, original SHA, full source context/revision, result SHA, approved field names, normalized submitted-profile SHA and approval actor/time. It is part of the **same atomic Candidate update**, not a separate job approval flag that might commit without saving facts. Job evidence remains immutable; a subsequent Candidate change makes its old result obsolete. The receipt is historical: later manual edits retain its original actor/time/hash while the existing review metadata records later corrections. It is not an automatic hiring decision, durable-source manifest, legal audit archive, AI assertion or proof of external storage recovery.

Candidate detail links to the existing editor only for current successful facts and update access. The editor makes no automatic processing request. Load retrieves current-source evidence and checks the HTTP parent's `parentUpdatedAt` against the loaded profile, so even same-revision/timestamp-only changes cannot mix drafts. Loading never changes fields. Explicit Apply imports bounded nonempty scalar/list/history facts, preserves missing fields and real zero, and keeps all fields editable; the existing HR confirmation checkbox starts unchecked and is mandatory for an approval save. No facts are auto-saved. New CV selection clears the old approval; context/unmount aborts pending loads. A failed 409 preserves HR corrections, unchecks confirmation and retains the proof (no silent fallback to an ordinary save). Reload/current review is required to resolve a stale source. Primary auth/parent failures mask editing; auxiliary child/500/503 errors retain the draft. Language changes make zero processing requests; StrictMode stays enabled. AZ/EN/RU copy states that extraction is rule-based.

Evidence: `Backend/tests/hrCvApproval.test.cjs` uses actual owned loopback Mongo/HTTP/JWT/DOCX, all five allowed scopes, independent mixed denial, source/stamp/state failures, refreshed old-JWT denial, final source/assignment CAS, concurrent save and immutable historical receipt. `Frontend/tests/hrCvApprovalUI.test.cjs` uses actual StrictMode browser/detail/editor/Bearer JSON/save, zero/unknown/manual corrections, no PUT before confirmation, primary/secondary failures, stale source, route/permission cancellation and three-language zero refetch. The combined targeted suite including earlier processing/retry/manual review is 110/110. External provider/storage/OCR/AI/ingestion readiness is not claimed.

## 10C5B — draft validation/replacement safety

A rejected file selection is validated before changing draft/source/approval state; it cannot silently erase the approval proof and bypass the mandatory confirmation checkbox. An actual valid replacement unmounts/aborts old job evidence and clears its proof. Saving the new file uses the existing multipart contract and creates pending extraction review for that new original, without inheriting old job provenance; old original bytes are preserved. Combining a replacement with an old approval proof is rejected 400 on the server and only the newly generated rejected upload is removed by existing owned-file cleanup.

Processing review metadata (bounded evidence/source/confidence, warnings/correction arrays and known scalar/list/history fields) is validated before render/apply. Malformed auxiliary review data yields a readable error while retaining the primary editable profile. Both discovered defects were reproduced on `62cb10a`; actual browser and HTTP/DOCX/owned-DB regressions prove the fixes. These are local contract tests, not external provider or storage durability tests.
